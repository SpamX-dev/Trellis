# Описание пакета агента

## Источник

[Схема пакета](agent-package.schema.yaml) задаёт одну ограниченную задачу. `agent.yaml` содержит устойчивый `id` с доменным префиксом, `domain`, требуемый адаптер внешнего исполнителя, ссылки на схемы входа и выхода, каталог навыков и типизированные гейты. Выпускная версия и контрольная сумма относятся к собранному пакету Registry, поэтому в авторском YAML не дублируются. Поле `domain` и имя пакета не предоставляют проектных прав.

Поле `instructions` указывает на `AGENTS.md` рядом с `agent.yaml`. Файл объясняет цель, короткую процедуру, вход, выход и условия остановки. Каждый навык находится в собственном каталоге с `skill.yaml` по [схеме навыка](skill.schema.yaml): имя, авторская инструкция, ссылки на схемы и при необходимости проверяемые примеры. Навык не задаёт отдельный жизненный цикл или машинный гейт.

Пути разрешаются относительно файла, который содержит ссылку, и остаются внутри снимка Framework. Ссылки на схемы могут завершаться JSON Pointer. Для каждой целевой схемы собирается замкнутый набор всех достижимых `$ref`; сетевые схемы и выход за Framework недопустимы. В этом формате контекста поддерживаются локальные `$ref` с JSON Pointer, без вложенных `$id` и динамических ссылок. Проверяющий использует зарегистрированные объекты схем, а текст для агента формируется из этих же объектов с раскрытием каждого достижимого целевого фрагмента. Неизвестный фрагмент блокирует сборку.

## Гейты

Гейты в `agent.yaml` имеют устойчивый `id`, фазу и один из известных типов проверки. Обязательные `input_schema` и `output_schema` проверяют данные по схемам, указанным в `input.schema` и `output.schema`. Дополнительные типы первого формата:

| Проверка | Фаза | Условие |
| --- | --- | --- |
| `knowledge_changeset_valid` | `before_complete` | Knowledge проверил ChangeSet из поля результата `value` на закреплённых ревизиях. |
| `knowledge_branch_matches_changeset` | `before_complete` | Knowledge подтвердил опубликованный commit ветки предложения и совпадение его итогового снимка с применением ChangeSet к базовой ревизии. Поля результата указаны JSON Pointer `changeset` и `proposal`. |
| `knowledge_changed_paths_allowed` | `before_complete` | Knowledge сравнил опубликованный commit из `proposal` с закреплённой базовой ревизией. Каждый изменённый путь, включая оба пути при переименовании, должен совпадать с точным путём в `allowed.paths` либо находиться под одним из каталогов `allowed.prefixes`. Поле `allowed` указывает JSON Pointer во входе задачи; префикс оканчивается `/` и совпадает только по границе каталога. Удаление также считается изменением. |
| `knowledge_revision_valid` | `before_complete` | Knowledge подтвердил опубликованный commit ветки из `proposal`, проверил весь итоговый снимок документов и их ссылки по закреплённым схемам Framework, а каждый изменённый документ домена результата — по единственной схеме навыка `skill`. Гейт ссылается на имя навыка, поэтому машинная проверка и текст агента используют один и тот же фрагмент схемы. |

`before_run` применяется до назначения исполнения, `before_complete` — до завершения задачи. Tasks координирует результат проверок; Runtime передаёт результат попытки и не принимает документы. Семантические критерии `x-trellis-checks` входят в контекст агента и отчёт проверки, но не являются детерминированным гейтом. Недоступность Knowledge или непрошедшая проверка не дают успешного результата гейта.

Для Git-гейтов Knowledge использует проект и базовую ревизию из задачи, а не из вывода агента. Ветка должна указывать на заявленный commit. ChangeSet для пакета с `knowledge_revision_valid` выводится из diff между базовой и итоговой ревизиями; агент не возвращает второе, потенциально расходящееся описание изменения. Область чтения и список разрешённых изменений сужают доступ задачи, но не выдают агенту проектных прав. Реализация исполнения этих гейтов в Tasks и Knowledge остаётся следующим этапом.

## Пакеты

[Пакет product](../domains/product/agent/module.md) описывает `product.capture-requirements` и подключён через `domains.yaml`. Он принимает запрос и список текущих требований, который может быть пустым. Навык включает составную схему из восьми файлов типов. Итоговые документы хранятся в Git-ревизии предложения; выход содержит ветку и точный commit. Проект и базовые ревизии задаёт задача Tasks. Статическая проверка пакета не подтверждает работу Registry, Runtime, Knowledge и реальный push.

[Пример compliance-check](../examples/compliance-check-agent-package/module.md) описывает оценку одного продукта по выбранным ограничениям. Он читает документы `product`, `compliance` и существующие оценки `compliance-check`, пишет только в перечисленные пути или каталоги домена результата и возвращает опубликованную ветку с commit. Его навык указывает на `domains/compliance-check/schema.yaml#/$defs/compliance-assessment`; гейт разрешает ту же схему по имени навыка. Учебный commit проверяется только по форме.
