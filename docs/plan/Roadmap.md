# Дорожная карта MVP Trellis по пользовательским историям

## Результат MVP

Установить один VSIX на Windows x64 → открыть или добавить папку в workspace через Explorer → увидеть её в Trellis → выполнить анализ → открыть граф → задать агенту Cursor вопрос о вызывающем коде → проверить ответ по исходникам → изменить код и обновить анализ.

Источники: [UserStories.md](../requirements/UserStories.md), [Functional.md](../requirements/Functional.md), [NonFunctional.md](../requirements/NonFunctional.md).

Это план реализации. Наличие оболочки 0.1.0 даёт основу интерфейса, но не означает выполнения историй MVP. Календарные оценки появятся после проверки интерфейсов закреплённой ревизии Grafel и решений ниже; этапы здесь задают порядок и критерии выхода.

## Решения и условия начала

| ID | Решение | Принятое решение или открытый вопрос | Условие начала |
|---|---|---|---|
| D-01 | Связь папок с Explorer | Принято пользователем: Trellis показывает корневые папки текущего workspace через API редактора. Добавление — штатной командой редактора; собственного реестра и отдельного удаления в Trellis нет. US-03 и FR-03 исключены. | Закрыто. Сохранение и восстановление состава workspace остаётся ответственностью редактора; миграция отдельного списка не требуется. |
| D-02 | Способ открытия dashboard | Использовать dashboard Grafel. Проверить пригодность Webview и переходов между проектами; согласовать Webview либо системный браузер. | До реализации US-07. |
| D-03 | Контрольный проект, язык и бюджеты ресурсов | Пользователь решил создать контрольный проект, когда он понадобится. Перед проверкой индексации определить язык/стек и подготовить проект с известными сущностями и связями. Аппаратную конфигурацию и допустимое время/RAM анализа определить к приёмке. Общая заявленная поддержка языков Grafel не заменяет проверку. | Сейчас не блокирует планирование. Проект и эталоны — перед проверкой US-05; численные пороги — до приёмки US-05/US-06. |
| D-04 | Владение движком и данными при нескольких окнах | Проверить возможности отдельного экземпляра на контекст и безопасного совместного использования. Определить адреса, идентификацию, блокировки, маршрутизацию запросов и завершение последнего владельца. | До реализации US-04. |

Решения D-02/D-04 начинают с проверки кода и интерфейсов закреплённого Grafel, включая возможность изолировать данные, управлять проектами и сохранять предыдущий индекс. Если выбранное решение меняет архитектурную границу, оно согласуется и документируется рядом с этой границей. Неизвестная возможность движка не считается готовой функцией.

Поставка для этого плана следует корневому `module.md`: движок и dashboard внутри одного VSIX. Допустимый пользователем вариант самостоятельной загрузки зависимостей остаётся альтернативой; переход к нему требует явного обновления требований и решения о поставке.

## Этапы и зависимости

| Этап | Пользовательский результат | Истории | Зависимости |
|---|---|---|---|
| 1 | Trellis работает с теми же папками, что Explorer | US-02; часть US-09 | Принятое D-01 |
| 2 | Устанавливаемый плагин самостоятельно поднимает свой движок | US-01, US-04; часть US-09 | D-04; этап 1 для контекста проектов |
| 3 | Выбранный проект можно проиндексировать | US-05; часть US-09 | Этапы 1–2, D-03 |
| 4 | Изменения кода отражаются в новом результате | US-06 | Этап 3 |
| 5 | Пользователь исследует проект в dashboard | US-07 | Этапы 3–4, D-02 |
| 6 | Агент Cursor работает с правильным проектом через MCP | US-08 | Этапы 3–4, D-04 |
| 7 | Все восемь историй MVP подтверждены на едином поставляемом артефакте | US-01, US-02, US-04–US-09; завершение US-09 | Этапы 1–6, закрытые D-01–D-04 |

Проверку сборки и контрактов Grafel можно выполнять независимо от уточнения интерфейса папок. Этапы dashboard и MCP технически независимы после подготовки индекса; указанный порядок сначала даёт пользователю видимый результат. US-03 и FR-03 исключены из всех этапов; обработка изменения workspace относится к US-02 и контексту операций.

## Этап 1 — Папки Explorer: US-02

Результат на 2026-09-15: реализация и проверки VS Code выполнены для VSIX 0.2.1 с пустой вкладкой и командами в заголовке боковой панели. Проверка Cursor отложена по указанию пользователя; приёмка в обоих редакторах пока не закрыта. Артефакт, сценарии и ограничения зафиксированы в [Stage1Acceptance.md](Stage1Acceptance.md).

Работы:

1. Сохранить текущий источник данных `vscode.workspace.workspaceFolders` в соответствии с D-01 и проверить связь боковой панели с Explorer. По уточнению пользователя список папок отображается только в панели; вкладка остаётся пустой до подключения Grafel.
2. Сохранить штатную команду добавления папки и переход к папке в Explorer. Отдельный реестр и команда удаления не создаются.
3. Подготовить выбор проекта для анализа по URI папки текущего workspace.
4. Дополнить пустое состояние и диагностику недоступной или неподдерживаемой для анализа папки; проверить обновление при изменениях workspace.
5. Разместить команды проверки доступности и открытия журнала в заголовке боковой панели. Открытие пустой вкладки оставить только в палитре команд.

Приёмка: открыть папку, добавить вторую одноимённую папку штатной командой Trellis и сравнить Explorer с боковой панелью. Отменить диалог добавления; открыть сохранённый workspace после перезапуска; изменить состав workspace средствами редактора и проверить обновление Trellis. Проверить пустой workspace, команды доступности и журнала в заголовке панели, отсутствие отдельной команды удаления и пустую вкладку, открываемую из палитры. Проверка изменений workspace не требует разработки собственной операции удаления.

Граница: `plugin/src/ide` и точка композиции; источником состава папок остаётся API редактора.

Требования: FR-02, FR-09; NFR-03, NFR-04, NFR-07.

## Этап 2 — Установка и движок: US-01, US-04

Работы:

1. Проверить сборку движка/dashboard на Windows x64 и включить их в VSIX с версиями и уведомлениями о лицензиях.
2. Закрыть D-04, реализовать подготовку, запуск, проверку совместимости/готовности и освобождение ресурсов.
3. Изолировать Trellis от отдельно установленного Grafel и защитить запуск от дублей и чужого сервиса на адресе.
4. Показать состояния движка, ошибки подготовки и действие повторного запуска.

Приёмка: установка VSIX без внешнего Grafel и инструментов сборки; запуск в VS Code и Cursor; повторная установка; два окна; занятый адрес; несовместимый компонент; аварийное завершение и восстановление. Проверить освобождение последнего процесса и сохранение работоспособности другого окна.

Границы: `scripts`, `plugin/src/runtime`, `plugin/src/grafel`, `plugin/src/ide`; изменения движка — внутри fork `grafel/` с обновлением ссылки submodule.

Требования: FR-01, FR-04, FR-09; NFR-01–NFR-05, NFR-08.

## Этап 3 — Первый анализ: US-05

Работы:

1. Подтвердить необходимые команды/API Grafel. Перед проверкой индексации определить язык/стек и создать контрольный проект с эталонными сущностями и связями по D-03.
2. Связать команду индексации с выбранным проектом и ограничить параллелизм.
3. Отображать состояние, время успешного анализа, доступную статистику и ошибки.
4. Проверять доступность результата через адаптер Grafel; обработать отсутствие поддерживаемого кода.
5. Проверить запуск только для папки текущего workspace в доверенном контексте. При изменении workspace уже начатая операция не должна переключаться на другой проект.

Приёмка: первый анализ подготовленного контрольного проекта с проверкой определений и связей; двойной запуск; недоступная папка; авария движка; пустой/неподдерживаемый проект. Измерить время и ресурсы, согласовать бюджеты D-03. Размер контрольного проекта должен быть указан в отчёте: функциональный пример не подтверждает производительность на больших проектах.

Границы: `plugin/src/grafel`, `plugin/src/runtime`, `plugin/src/ide`; алгоритмы анализа остаются в Grafel.

Требования: FR-02, FR-04, FR-05, FR-09; NFR-03–NFR-06, NFR-08.

## Этап 4 — Обновление результата: US-06

Работы:

1. Реализовать ручной повторный анализ и согласованное переключение на успешный результат.
2. Сохранять предыдущий результат при ошибке; показывать его время отдельно от последней попытки.
3. Восстанавливать состояния после перезапуска и проверять совместимость сохранённого индекса.

Приёмка: добавить и удалить контрольную связь, повторить анализ и проверить оба изменения через адаптер; прервать следующее обновление и проверить сохранность предыдущего результата. Повторить проверку после перезапуска редактора. Проверки через dashboard и MCP повторяются на этапах 5–6.

Границы: `plugin/src/grafel`, `plugin/src/runtime`, `plugin/src/ide`; при необходимости безопасного сохранения индекса — fork Grafel.

Требования: FR-05, FR-06, FR-09; NFR-04–NFR-06, NFR-08.

## Этап 5 — Dashboard: US-07

Работы:

1. Закрыть D-02 и открыть существующий dashboard с контекстом выбранного проекта.
2. Проверить поиск сущности, просмотр связей и местоположений в исходниках.
3. Обработать отсутствие индекса, потерю движка и изменение доступного контекста при изменениях workspace.
4. Проверить появление нового результата после повторного анализа.

Приёмка: два проекта workspace с различимыми данными, переключение между ними, повторное открытие без нового движка, ошибка подключения, изменение workspace и проверка обновлённой связи. Зафиксировать оставшиеся ограничения dashboard.

Границы: `plugin/src/ide`, `plugin/src/grafel`; web-интерфейс принадлежит Grafel.

Требования: FR-02, FR-06, FR-07, FR-09; NFR-03, NFR-05–NFR-08.

## Этап 6 — MCP в Cursor: US-08

Работы:

1. Проверить механизм настройки на целевой версии Cursor; реализовать подключение и отключение собственной записи без потери остальных.
2. Привязать запросы к проекту/контексту по D-04, исключить незаметную смену адресата запроса.
3. Выполнить реальное обнаружение инструментов и запрос из агента Cursor.
4. Проверить ошибки без индекса, повторный анализ и разрешение новых запросов только в папки текущего workspace.

Приёмка: подключить дважды и проверить отсутствие дублей; задать контрольный вопрос о вызывающем коде; сопоставить ответ инструмента с исходниками; изменить код, переиндексировать и повторить запрос. Проверить два workspace, смену их состава, отключение MCP и сохранность посторонних настроек.

Границы: `plugin/src/ide`, `plugin/src/grafel`, `plugin/src/runtime`; MCP-инструменты и анализ принадлежат Grafel.

Требования: FR-02, FR-06, FR-08, FR-09; NFR-03, NFR-04, NFR-06, NFR-08.

## Этап 7 — Сквозная приёмка: US-01, US-02, US-04–US-09

Диагностика US-09 реализуется вместе с операциями на каждом этапе. Здесь подтверждается её полнота и работа всего продукта из одной поставки.

Обязательный сценарий:

1. Установить итоговый VSIX в проверяемую чистую Windows-среду. Зафиксировать checksum, версии и ревизию Grafel.
2. Добавить контрольный проект в workspace, сохранить workspace средствами редактора, открыть его после перезапуска и проверить совпадение папок Explorer и Trellis.
3. Выполнить анализ, проверить ожидаемые сущности и связи, открыть dashboard.
4. Подключить MCP в Cursor и выполнить контрольный запрос из агента.
5. Изменить код, переиндексировать и проверить добавленную/удалённую связь в обоих каналах.
6. Воспроизвести ошибку, найти её в журнале и восстановить работу без потери предыдущего успешного результата.
7. Изменить workspace средствами редактора и проверить актуальность папок и контекста операций Trellis, а также сохранность исходников.
8. Повторить применимые UI/runtime-сценарии в VS Code, проверить два окна и освобождение ресурсов.

История считается закрытой, когда выполнены все её критерии приёмки, применимые NFR подтверждены, а результат записан с версией артефакта. Итоговый отчёт должен содержать сценарии, ожидаемые и фактические результаты, контрольные ссылки на код, замеры и известные ограничения. Сборка, F5 и успешный health check по отдельности не являются приёмкой MVP.

## Что не расширяет этот план

Собственный набор папок и отдельное удаление в Trellis исключены решением D-01; они не запланированы на следующий этап автоматически. Автоматическое наблюдение за файлами, отмена анализа отдельной командой, собственный граф/чат, генерация документации, аудиты, Git-diff, облако, совместная работа, другие ОС и MCP-клиенты, межпроектный анализ и отдельная очистка кэша идут после MVP. Новое требование включается через пользовательскую историю с явным влиянием на текущие этапы.
