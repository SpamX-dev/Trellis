# Замена Trellis Framework на TypeScript-библиотеку

## 1. Цель и границы первого цикла

Удалить прежнее содержимое `trellis-framework` и построить небольшую TS-библиотеку вокруг одного сценария: агент описывает продукт и его требования.

Первый цикл включает:

- шесть типов документов: **Product, US, FR, NFR, BO, BP**;
- одного агента сбора требований и один навык;
- обычные TypeScript-типы, объекты, импорты и функции проверки;
- сборку файлового комплекта инструкций для внешнего агента;
- проверку результата задачи и документов из Git-снимка;
- сквозной пример на временном локальном Git-репозитории.

**Агент возвращает статус и краткое резюме. Документы находятся в Git.** Проверяющий код получает точную ревизию и её содержимое от вызывающего компонента.

UI Builder, запуск LLM, публикация в Registry, удалённый push, принятие изменений, остальные домены и универсальный конструктор в этот цикл не входят.

Работа идёт отдельными шагами: один шаг — один обозримый набор изменений с проверяемым результатом. После него фиксируем сделанное и оставшиеся ограничения; следующий шаг выполняем отдельной итерацией.

Текущая исходная точка проверена: старый `check`, 22 теста и сборки API/Web проходят. Работающий сервер Projects/Repositories старый Framework не импортирует.

## 2. Устройство библиотеки и публичная модель

### Организация

`trellis-framework` становится локальным npm workspace-пакетом `@trellis/framework`, пока без публикации.

```text
trellis-framework/
  package.json
  tsconfig.json
  README.md
  module.md
  src/
    index.ts
    agent.ts
    validation.ts
    product/
      module.md
      model.ts
      validation.ts
      agent.ts
      skill.ts
      instructions.md
      skill.md
    node/
      module.md
      index.ts
  examples/
    product/
  test/
```

Это начальная карта. Файлы появляются на соответствующем шаге; заранее создаются только обозначенные крупные границы с `module.md`.

Ответственность частей:

- Корень библиотеки — небольшие общие типы агента, навыка, гейта и результата проверки.
- `product` — конкретная модель четырёх документов и её поведение.
- `node` — чтение ресурсов, YAML и файловая сборка.
- `examples/product` — конкретный сценарий, включая чтение временного Git-репозитория.

Публичные точки входа: `@trellis/framework`, `@trellis/framework/product`, `@trellis/framework/node`. Корневой импорт не выполняет файловые операции и не запускает процессы.

### Документы

Сохраняем узнаваемые названия полей, убирая зависимости от отложенных сущностей.

| Тип | Основные поля |
|---|---|
| Product | `id`, `type`, `name`, `purpose`, `boundary` |
| US | `id`, `type`, `name`, `product_ref`, `actor`, `goal`, `benefit` |
| FR | `id`, `type`, `name`, `product_ref`, `statement`, `acceptance_criteria`; необязательные `trigger`, `story_refs`, `object_refs`, `constraint_refs` |
| NFR | `id`, `type`, `name`, `product_ref`, `kind`, `statement`, `measure`, `target`, `context` |
| BO | `id`, `type`, `name`, `product_ref`, `definition`, `attributes` |
| BP | `id`, `type`, `name`, `product_ref`, `goal`, `steps`; шаг: `key`, `name`, необязательные `actor`, `requirement_refs`, `next_steps` |

Значения `type`: `product`, `user-story`, `functional-requirement`, `non-functional-requirement`, `business-object`, `business-process`.

Общие необязательные поля: `summary`, `group`, `sources`, `gaps`. Источник содержит обязательный `location` и необязательный `quote`. `group` остаётся списком точных имён без отдельного каталога.

Для NFR сохраняем категории `performance`, `reliability`, `security`, `usability`, `maintainability`, `compatibility`, `other`.

`actor` в US и шаге BP — содержательная строка; отдельного каталога ролей нет. `next_steps` шага ссылаются на локальные ключи шагов того же процесса.

### Вход, результат и проверки

Первый вход агента — `{ request: string }`. Существующие документы он читает из предоставленной рабочей копии. Подготовка рабочей копии и её разрешений принадлежит вызывающему компоненту.

Результат:

```ts
/** Отчёт исполнителя; сам по себе не подтверждает прохождение гейтов. */
interface TaskResult {
  status: 'completed' | 'needs_input' | 'failed';
  summary: string;
}
```

В результате нет документов, ChangeSet и повторного описания Git-изменений.

Публичные функции предусматривают:

- разбор неизвестных данных в `ProductDocument`, вход задачи и `TaskResult`;
- проверку полного набора продуктовых документов;
- проверку завершения задачи по результату и переданному Git-снимку;
- сборку комплекта конкретного product-агента.

Ошибки данных возвращаются структурированно: код, путь к полю или файлу, сообщение. Ошибки чтения и сборки завершают соответствующую операцию с диагностикой.

## 3. Последовательность маленьких шагов

### Шаг 1. Удаление старого Framework и создание собираемого пакета

Удалить старые `contracts`, `domains`, `examples`, YAML-конфигурации и описания их устройства. Старое содержимое остаётся доступно через историю Git; отдельный `legacy`-каталог не создаём.

Одновременно:

- удалить старый проверяющий скрипт и тесты, целиком завязанные на удаляемые схемы;
- создать npm-пакет, строгую ESM-сборку TypeScript и генерацию `.d.ts`;
- подключить workspace к корневым командам;
- вынести проверку Markdown-ссылок из старого проверяющего скрипта в самостоятельную служебную проверку;
- переписать README и `module.md` Framework;
- исправить ссылки и утверждения о старых контрактах в соседних модулях;
- убрать прямую зависимость от Ajv, если после удаления потребителей больше нет; Zod серверных модулей сохранить;
- обновить копирование package-манифестов в Dockerfile API и Web для работы `npm ci` с workspace.

Границу Knowledge Validation сохранить: она будет использовать библиотечные проверки, когда появится интеграция. Работающие серверные операции и данные не изменять.

**Готово, когда:** пакет собирается и импортируется, ссылки документации корректны, API/Web продолжают собираться. Старый валидатор больше не запускается скрыто через корневые команды.

### Шаг 2. Типы документов и согласованный пример

Добавить модель из предыдущего раздела и небольшой пример: по одному документу каждого из шести типов со связями.

Все типы, публичные функции и значимые поля снабдить русскими комментариями о смысле и ограничениях. Комментарии входят в декларации TypeScript.

Не вводить каталог доменов, регистрацию типов, наследование доменных моделей или описание полей через собственный DSL.

**Готово, когда:** пример проверяется компилятором, неверные типы полей выявляются, `.d.ts` содержат русские описания. Проверка внешних данных на этом шаге ещё не заявляется.

### Шаг 3. Проверка внешних данных обычными функциями

Реализовать разбор `unknown` без доверия к приведению `as ProductDocument`.

Проверять:

- известный тип документа и допустимый набор полей;
- обязательные значения и непустые строки;
- форму идентификатора: `^[A-Za-z0-9][A-Za-z0-9._-]*$`;
- допустимую категорию NFR;
- непустой список критериев приёмки FR;
- типы вложенных источников и элементов массивов;
- отсутствие повторов в `group` и списках ссылок.

Необязательные коллекции могут быть пустыми. Проверки не изменяют исходные объекты и не исправляют данные молча.

Общие вспомогательные функции ограничить чтением объекта, строки и массива и накоплением ошибок. Универсальный язык правил не строить.

**Готово, когда:** корректные данные возвращаются типизированными, ошибки указывают конкретное поле, отрицательные сценарии покрыты тестами.

### Шаг 4. YAML-документы и целостность снимка

YAML остаётся форматом документов в Git. Определения агентов и моделей в YAML больше не хранятся.

Для первого сценария фиксируем размещение:

```text
documents/product/<type>/<id>.yaml
```

Добавить строгий разбор YAML: отклонять повторяющиеся ключи, несколько документов в одном файле, aliases, anchors, merge и пользовательские теги.

Проверка продуктового снимка:

- ровно один Product в проверяемой области;
- остальные документы относятся к нему;
- идентификаторы уникальны;
- имя файла и каталог соответствуют `id` и `type`;
- пути не конфликтуют, включая различие только регистром;
- ссылки FR ведут соответственно на US, BO и NFR, а шаги BP — на FR;
- отсутствующие цели и неверные типы целей дают ошибки.

US, FR и NFR могут отсутствовать в конкретной итерации. Полный учебный пример содержит все шесть типов.

Связи извлекаются прямым кодом из известных полей. Общий графовый движок и постоянный индекс пока не вводятся.

**Готово, когда:** порядок файлов не влияет на результат, висячие ссылки и дубли обнаруживаются, перенос старых JSON Schema не требуется.

### Шаг 5. Агент и навык как TS-экспорты

Добавить `productAgent` и `captureRequirementsSkill`.

Определение агента непосредственно связывает:

- задачу и инструкцию;
- функцию проверки входа;
- импортированный навык;
- функцию проверки отчёта;
- функции гейтов.

Markdown подключается как ресурс через URL относительно модуля. Строка означает готовый текст; файловый URL — ресурс, который читает сборщик. Произвольного поиска имён и разрешения конфигурационных путей нет.

Инструкция требует прочитать текущие документы, подготовить изменения, записать их в предоставленную Git-рабочую копию, создать commit и вернуть статус с резюме. Недостающие сведения не выдумываются.

**Готово, когда:** определение импортируется обычным TS-кодом, связи видны через переход к экспортам, несовместимые сигнатуры обнаруживает компилятор.

### Шаг 6. Гейты завершения по Git-артефактам

Вызывающий код передаёт библиотеке точный commit и содержимое файлов продуктовой области из него. Получение настоящего снимка и проверка проектных прав остаются за вызывающим компонентом.

Для первого агента достаточно двух гейтов:

1. Для `completed` предоставлен Git-снимок с продуктовым результатом.
2. Документы снимка проходят структурную проверку и проверку связей.

`needs_input` и `failed` являются допустимыми отчётами исполнителя, но не успешным завершением. Гейты завершения для них отмечаются как не выполнявшиеся.

Сообщение `completed` при отсутствующем снимке или неверных документах не даёт успешного итога проверки. Содержательная правильность требований не объявляется доказанной.

**Готово, когда:** тесты различают отчёт исполнителя и подтверждённый результат гейтов, включая ложное заявление об успехе.

### Шаг 7. Сборка файлового комплекта агента

Добавить конкретную сборку product-агента, без универсального упаковщика произвольных модулей.

Комплект содержит:

- `AGENTS.md`;
- текст навыка;
- сгенерированные `.d.ts` используемых моделей с комментариями;
- примеры входа, отчёта и четырёх документов.

Сборщик использует декларации из той же сборки библиотеки. Нужные зависимости деклараций включаются с сохранением их относительного расположения.

Комплект предназначен для передачи контекста внешнему агенту. Исполняемые проверки остаются экспортами библиотеки; доставка их версий через Registry — следующий отдельный этап.

Выход по умолчанию — внутри игнорируемого `var/agents/product`. Сборка не читает секреты, рабочие документы проекта или произвольные каталоги. Запись ограничена каталогом результата.

**Готово, когда:** комплект можно скопировать в другое место и прочитать без исходного дерева Framework; все его ссылки разрешаются, недостающий ресурс блокирует сборку.

### Шаг 8. Сквозной локальный пример

Создать временный Git-репозиторий, записать туда учебные документы и сделать настоящий локальный commit.

Пример:

1. собирает комплект агента;
2. использует подготовленный отчёт `completed` с резюме;
3. читает файлы по точному commit;
4. передаёт снимок библиотеке;
5. выводит результаты гейтов.

Затем отдельными тестами проверяет испорченные документы и отсутствие необходимых артефактов. Незакоммиченные изменения рабочей копии не должны влиять на проверку выбранного commit.

Это проверка сборки, Git-адаптера примера и детерминированных гейтов. Настоящий агент пока не запускается.

**Готово, когда:** сценарий воспроизводится одной документированной командой, а ошибки приводят к неуспешному результату и понятной диагностике.

## 4. Проверки и критерии завершения

Корневые команды должны явно проверять новую библиотеку:

- `npm run check` — типы Framework и ссылки документации;
- `npm test` — тесты новой модели, проверок и сборки;
- `npm run build` — Framework, существующие API и Web;
- `npm run build:agent:product` — файловый комплект;
- `npm run example:product` — локальный Git-сценарий.

Обязательные отрицательные случаи: неизвестное поле или тип, пустое обязательное значение, неверная категория NFR, повтор ID, отсутствующая ссылка, неправильный тип цели, расхождение пути и документа, неоднозначный YAML, потерянный Markdown-ресурс и `completed` без корректных Git-артефактов.

После изменения workspace проверить также сборку обоих Docker-образов. Изменения не требуют перезапуска работающих сервисов или миграции их данных.

Старые 22 теста не считаются автоматически перенесёнными: новая версия покрывает только явно выбранный первый сценарий.

## 5. Зафиксированные ограничения

- Чистый старт без совместимости со старой конфигурацией Framework и без переноса всех прежних возможностей.
- Бизнес-правила (BR) исключены из первого цикла: единственная связь у них была с FR, а правило предметной области перекрывается с поведением FR. Вернуть тип стоит, когда появится второй потребитель — например, ссылки из BO или BP.
- Формат документов в Git остаётся YAML; авторская модель и поведение определяются TypeScript-кодом.
- Проверяется один продукт в переданной области снимка.
- Статус, резюме и Git-артефакты имеют разные роли; документы не дублируются в ответе агента.
- JSON Schema, генерация валидаторов и собственный язык конфигурации отсутствуют.
- README описывает запуск и текущие ограничения; `module.md` — ответственность и границы без статуса реализации.
- Первой реализационной итерацией будет только **шаг 1**.
