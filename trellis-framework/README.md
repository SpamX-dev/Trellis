# Trellis Framework

Исходные контракты, из которых компоненты Trellis получают схемы проверки, контекст агента, правила размещения документов и человекочитаемые представления.

## Структура

- [contracts](contracts/module.md): документ, конфигурация домена и жизненный цикл изменения.
- [domains](domains/module.md): продукт, комплаенс и проверка комплаенса.
- [examples](examples/module.md): согласованный набор YAML-документов, предложение правки и учебный пакет проверки комплаенса.
- [domains.yaml](domains.yaml): ссылки на схему и агента каждого домена; рендер подключается при наличии правил.

## Действующая конфигурация домена

Домен связывает следующие артефакты:

| Артефакт | Содержание |
| --- | --- |
| schema | JSON Schema типов документов; описания, цели ссылок и смысловые критерии. |
| agent | Ответственность, инструкции и навыки со ссылками на схемы. |
| render | Необязательные подписи и порядок полей для чтения и сравнения документов. |

Схемы написаны в диалекте JSON Schema 2020-12. Поддержка в редакторе проверяется отдельно; проверка репозитория использует [Ajv 2020](https://ajv.js.org/json-schema.html#draft-2020-12-breaking). Собственные аннотации регистрируются явно при сохранении строгой проверки схем.

В [product](domains/product/module.md) активная конфигурация указывает на пакет ограниченной задачи. Его схема составлена из восьми файлов типов; представление оставлено [отдельной границей](domains/product/render/module.md) без правил. В `compliance` и `compliance-check` действуют прежние определения агента со встроенными навыками и рендер.

## Целевой пакет агента

Один пакет отвечает за одну ограниченную задачу с определёнными входом и выходом. Внутри задачи `AGENTS.md` может описывать короткую процедуру, например подготовку документов, проверку, commit и push в ветку предложения. Последовательность разных задач пакетом не задаётся.

Исходное YAML-определение агента связывает его с доменом, схемами входа и выхода, отдельными каталогами YAML-навыков и детерминированными гейтами. Гейты объявляются в YAML для механической проверки Tasks. `AGENTS.md` объясняет цель, процедуру и условия остановки, но не заменяет проверяемые условия. Смысловые `x-trellis-checks` доступны агенту для оценки и не становятся детерминированными гейтами.

При сборке все ссылки на схемы, их `$ref`-зависимости, критерии и примеры разрешаются внутри зафиксированной ревизии Framework и включаются в пакет. Tasks проверяет вход и выход по схемам из пакета. Runtime передаёт агенту текст, в котором каждая достижимая ссылка на схему раскрыта до целевого фрагмента; этот текст формируется из тех же схем, без вручную переписанной версии правил. Источники знаний и порядок уточнений остаются частью авторских инструкций, а не выводятся из типов полей.

[Контракт пакета](contracts/agent-package.md) применён к [агенту product](domains/product/agent/module.md). Его вход включает запрос и текущие требования, которые могут отсутствовать на первой итерации; выход указывает ветку и commit, а документы US, FR, NFR, BR, BP и BD в отдельной итерации необязательны. [Пример проверки комплаенса](examples/compliance-check-agent-package/module.md) показывает другой пакет с выбранным каталогом ограничений. Сборка и доставка через CI/CD, а также исполнение Git-гейтов в Registry, Tasks и Runtime относятся к следующему этапу.
