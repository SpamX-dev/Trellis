# Trellis Framework

Протокол и схемы для работы с семантически связанными инженерными знаниями и трассируемыми изменениями.

## Назначение

Trellis Framework определяет общую модель данных и контракты взаимодействия компонентов Trellis. Контракты описывают инженерную работу от входящего изменения до обновления знаний, производных требований и связей с реализацией.

Framework используется независимо от конкретного хранилища, среды исполнения агентов и пользовательского интерфейса. Прикладные продукты не входят в состав проекта.

## Ответственность

- Спецификация Semantic Model: типы сущностей, отношений, инженерных областей, документов и ограничений.
- Схемы Knowledge State, Semantic Backlog, WorkItem, Knowledge Slice и ChangeSet.
- Контракты Agent Role и Skill, включая допустимые входы, доступ к знаниям, результат и требования к Evidence.
- Модель Derivation/Provenance, review, Human/Policy Gate и ревизий.
- Правила структурной валидации, совместимости и версионирования протокола.
- Контракты трассировки изменений между инженерными областями и несколькими репозиториями.
- Модель применимости требований, Controls, общих способов реализации и их выбора в проектах.
- Контракты ImpactPlan, управляемых версий методов, подключения и независимых оценок покрытия.

## Вне области проекта

- Исполнение агентов, управление LLM, инструментами и MCP-соединениями.
- Хранение Knowledge State и эксплуатация базы данных.
- Публикация и установка пакетов агентов и навыков.
- Конкретные агенты, прикладные процессы и продуктовые интерфейсы.
- Интеграции с IDE, Git-провайдерами и трекерами задач.
- Анализ исходного кода, построение AST/LSP-модели и проверка корректности реализации по коду.
- SDK

## Основные понятия

| Понятие | Определение |
| --- | --- |
| Semantic Model | Типы сущностей и отношений, инженерные области, ограничения и правила распространения влияния изменений. |
| Knowledge State | Согласованное состояние инженерных знаний на определённой ревизии. |
| Semantic Backlog | Входящие изменения и обязательства, ожидающие обработки в инженерной области. |
| WorkItem | Типизированная единица Engineering Work: входы, задача, область, контекст, роль, навыки и контракт результата. |
| Engineering Work | Процесс интерпретации, проектирования или проверки знаний в рамках WorkItem. |
| Knowledge Slice | Ограниченный контекст WorkItem: сущности, отношения, пути зависимостей, ограничения и происхождение на заданной ревизии. |
| Agent Role | Контракт ответственности исполнителя: допустимые входы, область знаний, навыки, изменения и результаты. |
| Skill | Способ выполнения класса работ: retrieval policy, процедура, валидация, схема результата и требования к Evidence. |
| ChangeSet | Предлагаемый набор изменений сущностей, отношений и связанных артефактов относительно базовой ревизии. |
| Derivation | Запись преобразования конкретных входов в результаты Engineering Work. |
| Provenance | Происхождение знания: источники, ревизии, исполнители, версии навыков, преобразования и решения review. |
| Evidence | Проверяемые материалы или ссылки, подтверждающие утверждение, решение либо результат проверки. |
| Human/Policy Gate | Контрольная точка принятия ChangeSet человеком или согласно применимой политике. |
| Downstream requirements | Требования, выведенные из результатов работы и адресованные другим инженерным областям. |
| Control / Realization Pattern | Обеспечиваемое свойство и общий способ его обеспечения с условиями применимости. |
| Project Realization | Выбранные способы, контекст, точка приложения и версия реализации конкретного проекта. |
| MethodArtifact | Управляемая версия навыка или другого метода работы/проверки с нормативными зависимостями. |
| ImpactPlan | Обоснованный план влияния изменения на методы и проекты, включая неизвестные области. |
| CoverageAssessment | Оценка покрытия методами либо выполнения в проекте на фиксированных основаниях и Evidence. |
| AdoptionRecord | Подтверждённое подключение выбранных версий методов для новых запусков в указанной среде. |

Agent Role задаёт контракт работы; пакет агента предоставляет реализацию роли. WorkItem описывает работу; отдельный запуск агента является попыткой её выполнения.

## Требования и изменение методов

Skill является входом инженерной работы и может быть её управляемым результатом. Изменение требования интерпретируется в контексте Controls, способов реализации, проектов и инженерных областей. Граф предоставляет кандидатов влияния; агент обосновывает ImpactPlan, человек проверяет смысл изменения и план, а принятые пункты порождают WorkItems.

Одобрение плана, принятие результата, публикация и подключение версии имеют самостоятельную область действия. Работы над навыком не заменяют входные навыки текущего запуска. Переоценка неизменённого метода сохраняет старый пакет и создаёт новую запись покрытия.

Покрытие требования методами не означает его выполнения в существующем проекте. Эти выводы имеют независимые scope, Evidence и актуальность. Изменение существенной зависимости требует review прежнего вывода; история не переписывается.

## Связь с компонентами Trellis

| Компонент | Использование Framework |
| --- | --- |
| `trellis-runtime` | Выполнение WorkItem, применение контрактов Agent Role и Skill, формирование ChangeSet и Provenance. |
| `trellis-knowledge` | Хранение Knowledge State, проверка и применение ChangeSet, выдача Knowledge Slice. |
| `trellis-registry` | Проверка манифестов пакетов агентов и навыков и их совместимости с протоколом. |
| `trellis-vscode` | Отображение объектов протокола, управление работой и передача решений review. |

Зависимость направлена от компонентов к контрактам Framework. Framework не зависит от их реализаций.
