# Trellis Knowledge

Версионируемое хранилище семантических инженерных знаний, документов и состояния графа Trellis.

## Назначение

Trellis Knowledge хранит канонический Knowledge State и историю его изменений. Сервис предоставляет доступ к сущностям, отношениям, документам, Evidence и Provenance через контракты Trellis Framework.

Документы, структурированные знания и граф связаны общей моделью идентичности и ревизий. Физическое хранение этих данных может использовать одну или несколько технологий.

## Ответственность

- Хранение сущностей и типизированных отношений согласно Semantic Model.
- Версионирование Knowledge State, документов и ссылок на источники.
- Хранение Semantic Backlog, WorkItem и устойчивых записей результатов Engineering Work.
- Хранение предложенных ChangeSet, решений Human/Policy Gate и принятых ревизий.
- Проверка схем, ссылочной целостности, базовой ревизии и условий применения ChangeSet.
- Согласованное применение принятого ChangeSet с сохранением истории.
- Выдача Knowledge Slice по области, опорным сущностям, ограничениям и ревизии.
- Хранение Derivation/Provenance, Evidence и downstream requirements.
- Запросы трассировки, различий ревизий и зависимостей для анализа влияния.
- Multi-repo traceability между инженерными знаниями и артефактами реализации.
- Хранение нормативных зависимостей методов, планов влияния и подтверждённых записей подключения версий.
- Отдельные оценки покрытия методами и выполнения в проектах с основаниями актуальности.

## Вне области проекта

- Исполнение агентов, выбор LLM и управление инструментами или MCP-сессиями.
- Разработка инженерных решений и автоматическое принятие содержательных выводов агента.
- Публикация и разрешение пакетов агентов и Skills.
- Пользовательский интерфейс review и управление локальной средой разработчика.
- Анализ исходного кода, построение AST/LSP-модели и замена Git.
- Определение архитектурных границ по структуре репозиториев.

## Основные понятия

| Понятие | Содержимое |
| --- | --- |
| Semantic Model reference | Ссылка на применимую версию модели типов, отношений и ограничений. |
| Knowledge State | Согласованный набор знаний на определённой ревизии. |
| Elements / Relations | Требования, решения, системы, компоненты, задачи и типизированные связи между ними. |
| Documents | Исходные документы и представления знаний со ссылками на источники или ревизии графа. |
| Semantic Backlog / WorkItem | Входящие обязательства области, описание работ, состояния и связи с результатами. |
| ChangeSet / Revision | Предложение изменения и зафиксированное состояние после его принятия. |
| Derivation/Provenance | Происхождение сущностей и результатов, включая WorkItem, Agent Role и версии Skills. |
| Evidence | Проверяемые материалы, результаты внешних проверок и ссылки на их версии. |
| Knowledge Slice | Выборка контекста на заданной ревизии с явными границами и сведениями о полноте данных. |
| ImpactPlan | Изменение требования, рассмотренные области, пункты update/check/no_change, причины и пробелы. |
| MethodArtifact | Семантическое описание версии метода и точные ссылки на исходники, содержимое и пакет. |
| CoverageAssessment | Вывод в одной размерности, проверенные версии, существенные зависимости и Evidence. |
| AdoptionRecord | Подтверждённый выбор версий методов для целевой среды; не намерение и не факт публикации. |

Исходный документ сохраняет собственное происхождение. Документ, сформированный из графа, является представлением определённой ревизии Knowledge State. Изменение представления не должно незаметно изменять принятое состояние: семантические правки оформляются через ChangeSet.

## Основные интерфейсы

Концептуальный набор операций; названия не являются опубликованными API.

| Операция | Результат |
| --- | --- |
| Read state / revision | Состояние знаний или история его ревизий. |
| Query elements / relations | Сущности, связи и пути зависимостей в заданной области. |
| Build Knowledge Slice | Контекст по запросу Runtime с привязкой к ревизии и источникам. |
| Read document / Evidence | Содержимое или ссылка на материал с данными о версии. |
| Read / update Semantic Backlog | Обязательства, WorkItem и их состояния с сохранением истории. |
| Propose / inspect ChangeSet | Сохранённое предложение, semantic diff, document diff и результаты проверок. |
| Apply accepted ChangeSet | Новая ревизия либо объяснение конфликта или нарушения условий принятия. |
| Query traceability / derivation | Цепочки входов, решений, downstream requirements и артефактов реализации. |

Изменения принятого Knowledge State, включая downstream requirements, оформляются через ChangeSet. События исполнения и состояния обработки WorkItem сохраняются как записи процесса и не означают принятие предложенных знаний.

## Применение изменений

```text
Knowledge State at revision N
  + ChangeSet based on N
  -> schema and integrity validation
  -> draft state and diff
  -> Human/Policy Gate decision
  -> check decision scope and base revision
  -> apply ChangeSet
  -> Knowledge State at revision N+1
```

Knowledge сохраняет решение gate и проверяет условия применения. Получение решения человека или политики координирует Runtime; UI предоставляет клиент.

Конфликт ревизий не разрешается скрытой перезаписью состояния. История должна позволять установить, какое предложение было принято, кем или по какой политике и к какой ревизии оно относилось.

## Трассировка и влияние изменений

```text
Input requirement
  -> WorkItem / Engineering Work
  -> Decision
  -> Downstream requirements
  -> Implementation tasks
  -> Repositories / commits / reviews / Evidence
```

Одна сущность архитектуры может быть связана с несколькими репозиториями; один репозиторий может содержать реализации нескольких сущностей.

Knowledge предоставляет связи и историю для анализа влияния. Содержательная переоценка решений выполняется в Engineering Work. Наличие связи само по себе не доказывает влияние; используются правила Semantic Model. Неполное покрытие данных отмечается явно.

## Требования, методы и покрытие

Knowledge хранит requirement → control → realization pattern и связи с методами и реализациями проектов по [модели Framework](../trellis-framework/semantic-model/requirements-and-methods.md). Исследования, нормативные утверждения и описания методов могут происходить из одного документа. Нормативное принятие определяется ChangeSet и ревизией, а не типом исходного файла.

ImpactPlan хранится как версионируемое предложение. Review связывается с точными версиями изменения требования и плана. Принятые обязательства сохраняются даже при открытых работах и неизвестном покрытии. Для каждой пары «ревизия плана + пункт» сохраняется связь с WorkItem, чтобы повторная обработка не порождала дубликаты.

Запрос покрытия всегда указывает размерность `methods` или `project`, scope и ревизию/контекст оценки. Knowledge возвращает исторический результат и его актуальность раздельно. Изменение существенного основания даёт `needs_review` для текущего запроса; оно не переписывает прошлую оценку и не доказывает ошибку метода. Новая оценка может подтвердить прежний артефакт без изменения пакета.

Knowledge хранит связи и подтверждения, а Registry — содержимое опубликованных пакетов. Запись положительного покрытия требует Evidence в заявленной области. Обновлённый навык, наличие пакета или завершённая задача не создают автоматически положительную оценку проекта.

Концептуальные запросы расширяются чтением ImpactPlan, нормативных зависимостей метода, потребителей версии, AdoptionRecord и раздельных оценок покрытия. Условия принятия и повторы определены в [процессе изменения требований](../trellis-framework/workflows/requirement-change.md); [module.md](module.md) фиксирует границу компонента.

## Связь с компонентами Trellis

| Компонент | Взаимодействие |
| --- | --- |
| `trellis-framework` | Определяет схемы хранимых объектов и правила взаимодействия. |
| `trellis-runtime` | Читает знания, запрашивает Knowledge Slice, передаёт результаты работы и ChangeSet. |
| `trellis-registry` | Хранит пакеты; Knowledge сохраняет ссылки на использованные идентификаторы и версии пакетов в Provenance. |
| `trellis-vscode` | Показывает документы, состояние, изменения и трассировку через сервисные интерфейсы. |

## Пример структуры

Целевая организация репозитория:

```text
trellis-knowledge/
  state/       # Сущности, отношения и Semantic Backlog
  documents/   # Источники и представления знаний
  revisions/   # ChangeSet, решения gate и история
  provenance/  # Derivation и Evidence
  queries/     # Knowledge Slice, diff и traceability
  storage/     # Адаптеры физического хранения
  api/         # Сервисные интерфейсы
```
