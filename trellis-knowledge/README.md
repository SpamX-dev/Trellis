# Trellis Knowledge

Управление проектами, доступом, локальными Git-репозиториями, итоговыми артефактами агентов и принятыми YAML-документами по контрактам Framework.

## Внутренняя структура

| Подмодуль | Ответственность |
| --- | --- |
| [Identity](identity/module.md) | Подтверждение личности через сменного провайдера, идентичность пользователей, учётные записи и токены агентов. |
| [Keycloak](identity/keycloak/module.md) | Человеческие пользователи, регистрация, группы и глобальные роли; OIDC и локальное развёртывание в Docker с PostgreSQL. |
| [Projects](projects/module.md) | Создание, архивация, название, описание, владелец и проектные права. |
| [Repositories](repositories/module.md) | Git-транспорт, локальные репозитории, ревизии, файловые снимки, рабочие копии и публикация. |
| [Webhooks](webhooks/module.md) | Подписки на выбранные ветки, подпись и доставка уведомлений, журнал и повторы. |
| [Validation](validation/module.md) | Детерминированная проверка документов, ссылок и итогового предложения. |

Оркестрация принятия остаётся у Knowledge: он связывает проверку прав, проверку документов, решение человека и публикацию. Подмодули реализуют свои операции в этой общей границе.

## Пользователи и проекты

Keycloak обслуживает свободную регистрацию, вход людей, группы и назначение глобальных ролей. Личность пользователя связывается с парой `issuer` и `sub`, а не с изменяемым логином. Провайдер входа заменяем; проектные права и авторство решений остаются в Knowledge. Пароли людей принадлежат Keycloak.

| Роль | Полномочия |
| --- | --- |
| Глобальный `admin` | Создаёт и архивирует проекты, меняет настройки, назначает владельца. Само наличие этой роли не предоставляет права на содержимое. |
| Проектный `owner` | Управляет доступом пользователей и агентов к своему проекту; работает с документами и принимает изменения. |
| Проектный `user` | В назначенном проекте читает документы, готовит предложения, принимает или отклоняет изменения. |
| Агент | Читает назначенные проекты и публикует ветки предложений; не принимает изменения и не управляет настройками. |

Один человек может совмещать глобальную и проектную роли. Администратор назначается явно через роль `trellis-admin` в Keycloak; регистрация, в том числе самая первая, не выдаёт эту роль и не открывает существующие проекты. Администратор Keycloak и администратор Trellis имеют разные полномочия. Состав групп ведётся в Keycloak, но членство в них само по себе не предоставляет проектных прав: доступ назначается напрямую в Projects.

Каждый проект закрытый, имеет устойчивый ID, название, описание и одного владельца, назначаемого при создании. Создание завершается после готовности репозитория. Архивация запрещает публикацию, включая результаты уже запущенных задач, и сохраняет историю и чтение по действующим правам.

Агентов создаёт администратор через UI: название, токен Knowledge и список доступных проектов. Identity отвечает за выдачу, проверку и отзыв токена; Projects — за проектные назначения. Владелец управляет доступом агента к своему проекту. Опубликованная в Registry личность и навыки агента отличаются от этой учётной записи и не дают проектных прав. Управление учётной записью агента не предоставляет администратору права самостоятельно выдавать ему доступ к чужому содержимому. Токен агента независим от входа людей через Keycloak; секреты не хранятся в Git-документах.

## Хранение

Каждый проект хранится в отдельном локальном Git-репозитории на общем сервере. Repositories связывает ID проекта с расположением репозитория; изменение названия или пути не меняет идентичность проекта.

Принятое состояние — согласованный снимок каталога документов, зафиксированный точным commit ID. Для первого продуктового сценария размещение `documents/product/<type>/<id>.yaml` задаёт [план Framework](../trellis-framework/plan.md). Repositories разворачивает разрешённые снимки в локальные файлы для чтения, grep и построения графа. Он же загружает исторические ревизии. Наличие репозиториев на одном диске не предоставляет доступ ко всем проектам.

Граф строится по запросу из явно заданных ссылок. Он содержит область построения и ревизию источников. Отдельное хранилище графа и постоянный индекс для поиска по id не обязательны.

Рабочие копии агентов изолированы друг от друга и от принятых снимков. Runtime получает разрешённые снимки и инструменты через Knowledge; среда выполнения может дополнительно ограничить эти разрешения.

В целевом цикле итоговые отчёты и файлы агента хранятся в Knowledge с привязкой к проекту, задаче и исходным ревизиям отдельно от принятых YAML-документов. Состояние задачи, вопросы, ответы и журнал исполнения принадлежат [Tasks](../trellis-tasks/module.md). Сохранённый итог сам по себе не изменяет принятые документы.

## Запись

Агент или пользователь готовит рабочее предложение с одним или несколькими документами. Knowledge проверяет права и итоговый снимок, предоставляет различия клиенту, фиксирует решение уполномоченного человека и повторно проверяет права, состояние проекта и базовую ревизию перед применением. Validation проверяет переданный набор документов; решение о принятии остаётся за человеком.

Git-доступ использует стандартные clone/fetch/push; основной транспорт — HTTPS. Агенты публикуют ветки предложений. Принятая ветка `main` обновляется Repositories по решению Knowledge после проверок и человеческого принятия. Прямой push не обходит этот порядок; ни токен агента, ни глобальная роль администратора не заменяют решение уполномоченного участника проекта.

Создание, изменение и удаление документов проходит через предложение, проверку итогового снимка и решение человека. Выбор физического способа атомарной публикации снимка относится к реализации Knowledge.

## Уведомления

Repositories регистрирует событие опубликованного изменения Git-ветки. Webhooks доставляет подписанные уведомления внешним обработчикам по подпискам с фильтрами веток. Подписками как настройками проекта управляет глобальный администратор. Событие содержит идентификаторы события и проекта, ветку, предыдущую и новую ревизии и инициатора. Локальные правки и неопубликованные коммиты уведомлений не создают.

Доставка журналируется и допускает повторы; получатель обрабатывает событие идемпотентно. Ошибка доставки не отменяет Git-публикацию. Событие изменения ветки предложения не является `documents.accepted`: Knowledge создаёт событие принятия только после сохранения человеческого решения и согласованной публикации принятого снимка. Внутренние реакции на принятие организует Tasks, а назначенную им работу исполняет Runtime. Webhooks остаётся транспортом уведомлений для внешних обработчиков.

## Проверка репозитория

Проверка TypeScript-библиотеки Framework и локальных Markdown-ссылок запускается из корня:

```sh
npm run check
npm test
```

Текущий `check` проверяет компиляцию Framework, [пример продукта](../trellis-framework/examples/product/README.md) и ссылки документации; `test` проверяет разбор внешних значений, импорт точек входа и комментарии в декларациях. Проверка полного YAML-снимка и Git-гейтов появится следующими шагами [плана](../trellis-framework/plan.md). Код не записывает принятые документы и не моделирует надёжность файловых транзакций.

Сборка сервера и web UI из корня: `npm run build`. На Windows `powershell -File trellis-knowledge/server/test-integration.ps1` создаёт отдельную временную базу и запускает интеграционный сценарий в Docker с настоящими PostgreSQL и Git. Он проверяет создание, повтор после сбоя, роли, архивирование, чтение точного коммита и HTTP-токен агента.

## Локальный запуск первого этапа

1. Заполнить локальные `.env` по `identity/keycloak/.env.example` и `.env.example`. Они исключены из Git.
2. Запустить `docker compose -f trellis-knowledge/identity/keycloak/compose.yaml up -d --wait`. `trellis-realm.json` применяется только при первом создании realm; последующие изменения пользователей и ролей сохраняются в PostgreSQL.
3. Запустить `docker compose -f trellis-knowledge/compose.yaml up -d --build --wait` из корня проекта.
4. Открыть `http://localhost:8081/`, войти через Keycloak. API доступен web-клиенту через `/api`; серверный Git-том не опубликован.

Knowledge использует собственный PostgreSQL и отдельный том. Каталог назначаемых людей пополняется после их первого входа. Новый проект содержит лишь пустой стартовый коммит.

## Перенос на другой ПК

Оба ПК должны использовать Docker, эту версию конфигурации и одинаковый OIDC issuer (`http://localhost:8080/realms/trellis`). Снимок — разовая копия: после переноса изменения на ПК независимы. Команды запускаются из корня репозитория в Windows PowerShell. На исходном ПК должен работать текущий Keycloak с импортом только при первом запуске. После обновления Compose его нужно один раз пересоздать командой `docker compose -f trellis-knowledge/identity/keycloak/compose.yaml up -d --wait --force-recreate keycloak`; новый режим сохранит существующий realm.

```powershell
powershell -File trellis-knowledge/backup.ps1 -OutputPath D:\backups\trellis-snapshot
```

Команда временно останавливает Web, API и Keycloak, снимает согласованные копии двух PostgreSQL и Git-тома и запускает сервисы снова. Каталог снимка содержит `manifest.json`, `identity.dump`, `knowledge.dump` и `repositories.tar` с контрольными суммами. Храните его вне репозитория и переносите доверенным способом: он содержит учётные данные в виде хешей и содержимое проектов.

На целевом ПК сначала получите ту же версию кода, Docker и образы, затем выполните команду до первого запуска Trellis. На нём не должно быть контейнеров, томов или локальных `.env` Trellis. Скрипт откажется работать при несовпадении версий, миграций, issuer или контрольных сумм и никогда не перезаписывает существующее состояние.

```powershell
powershell -File trellis-knowledge/restore.ps1 -SnapshotPath D:\backups\trellis-snapshot
```

Восстановление создаёт новые локальные пароли подключения к PostgreSQL в исключённых из Git `.env`, поднимает сервисы и оставляет прежние пароли пользователей Keycloak и токены агентов действительными. Пароль администратора Keycloak также берётся из исходной базы, а не из нового `KC_BOOTSTRAP_ADMIN_PASSWORD` (он нужен лишь для пустой базы). После запуска откройте `http://localhost:8081/` и проверьте проекты и историю коммитов. При ошибке восстановления скрипт удаляет только контейнеры, тома и `.env`, созданные этим запуском.

## Граница реализации

Первый этап реализует OIDC-вход людей, агентские токены, проекты, назначения, отдельные bare Git-репозитории и чтение коммитов. Публикация веток, Git HTTPS, рабочие копии, принятие документов, MCP и доставка webhook остаются за пределами этого этапа. Точный [HTTP-контракт](contracts/projects-repositories.md) фиксирует ограничения и права.
