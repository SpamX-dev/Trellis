# Trellis Runtime

Среда исполнения агентов для выполнения Engineering Work по контрактам Trellis Framework.

## Назначение

Trellis Runtime реализует agent execution harness: получает WorkItem, разрешает Agent Role и Skills, формирует контекст, управляет исполнением и передаёт результат на проверку и принятие.

Runtime поддерживает проектирование новых систем и обработку изменений существующих систем. Во втором случае работа начинается с проверки текущего Knowledge State и оценки влияния входящего изменения.

## Ответственность

- Получение и выполнение WorkItem из Semantic Backlog.
- Разрешение пакета агента, его Agent Role, зависимостей и версий Skills.
- Формирование запроса Knowledge Slice с учётом роли, retrieval policy и базовой ревизии.
- Управление запуском, отменой, повторными попытками и восстановлением исполнения.
- Подключение моделей, инструментов и MCP в пределах разрешений выполнения.
- Проверка результата по Semantic Model, контрактам роли и навыков.
- Формирование ChangeSet, downstream requirements, Derivation/Provenance и ссылок на Evidence.
- Оркестрация Human/Policy Gate и передача принятого ChangeSet в Trellis Knowledge.
- Передача подтверждённых downstream requirements в Semantic Backlog целевых областей через контракты хранения.
- Сохранение событий исполнения и данных, необходимых для аудита работы.

## Вне области проекта

- Владение каноническим Knowledge State или его отдельной независимой копией.
- Реализация базы знаний, каталога пакетов и интерфейса IDE.
- Включение всех инженерных ролей и навыков в ядро Runtime.
- Самостоятельное одобрение изменений вне правил Human/Policy Gate.
- Встроенный анализ исходного кода, AST/LSP и доказательство корректности реализации.
- Подмена внешних инструментов разработки, систем контроля версий и CI.

Конкретные агенты и Skills поставляются пакетами. Результаты внешних инструментов могут включаться в Evidence и multi-repo traceability.

## Основные понятия и интерфейсы

Названия интерфейсов описывают их назначение; транспорт и публичный API подлежат спецификации.

| Понятие или интерфейс | Назначение |
| --- | --- |
| WorkItem / Engineering Work | Описание задачи и её выполнение; один WorkItem может иметь несколько попыток исполнения. |
| Execution Record | Входы, базовая ревизия, исполнитель, версии пакетов, события, результат и ошибки конкретного запуска. |
| Agent Role | Контракт допустимой работы, определённый Framework и реализованный пакетом агента. |
| Skill | Процедура, retrieval policy, валидация и контракт результата. |
| Knowledge access | Чтение Knowledge State, получение Knowledge Slice и передача ChangeSet в Knowledge. |
| Package resolution | Получение совместимых версий агентов и навыков из Registry. |
| Tool/MCP access | Предоставление инструментов агенту с учётом разрешений запуска. |
| Human/Policy Gate | Запрос review, получение решения и управление продолжением работы. |
| Derivation/Provenance | Связь входов, контекста, решений, downstream requirements и Evidence с конкретным выполнением. |

Knowledge Slice ограничивает контекст задачи и содержит ссылки на исходные знания и их ревизии. Runtime определяет необходимый контекст по контрактам роли и навыков; Knowledge выполняет запрос к хранимому состоянию.

## Процесс выполнения

```text
Semantic Backlog -> WorkItem
  -> Resolve Agent Role and Skills
  -> Request Knowledge Slice at base revision
  -> Execute Engineering Work
  -> Validate result
  -> Propose ChangeSet + downstream requirements + Provenance
  -> Human/Policy Gate
       approve -> Knowledge applies ChangeSet -> new revision
       amend   -> revise proposal -> validate -> gate
       reject  -> record decision

Accepted downstream requirements
  -> Semantic Backlog of target domains
```

Одобрение и применение являются отдельными шагами. Trellis Knowledge проверяет применимость ChangeSet к базовой ревизии. Конфликт требует актуализации контекста и повторной проверки изменённого предложения.

Downstream requirements сохраняют ссылки на исходные требования, решения и WorkItem. Они становятся обязательствами целевых областей после принятия соответствующего изменения. Отдельный результат работы может подтверждать актуальность существующего решения без перепроектирования системы.

Повторная попытка исполнения не должна повторно применять уже принятый ChangeSet или создавать дубликаты downstream WorkItem.

## MCP

Runtime управляет доступом агента к MCP-инструментам и lifecycle подключений. Адаптеры исполнения и работа с локальными или внешними MCP-серверами не зависят от VS Code.

Настройка подключения не заменяет разрешение на использование инструмента. Доступ определяется конфигурацией и политикой выполнения WorkItem.

## Связь с компонентами Trellis

| Компонент | Взаимодействие |
| --- | --- |
| `trellis-framework` | Определяет Semantic Model, схемы и контракты исполнения. |
| `trellis-knowledge` | Хранит Semantic Backlog и Knowledge State, выдаёт контекст, сохраняет результаты и применяет ChangeSet. |
| `trellis-registry` | Разрешает и предоставляет версии пакетов агентов и Skills. |
| `trellis-vscode` | Настраивает Runtime, инициирует работу, отображает результаты и передаёт действия пользователя. |

Runtime может использоваться другими клиентами без VS Code. Multi-repo traceability сохраняется через общие идентификаторы знаний и ссылки на артефакты разных репозиториев.

## Пример структуры

Целевая организация репозитория:

```text
trellis-runtime/
  execution/  # Lifecycle и оркестрация WorkItem
  context/    # Retrieval policy и запросы Knowledge Slice
  packages/   # Разрешение и загрузка пакетов
  tools/      # Адаптеры инструментов и MCP
  validation/ # Проверка результатов и обработка gate
  adapters/   # Подключения к моделям и сервисам Trellis
```

## Статус проекта

Стадия по текущей концепции: проектирование. README описывает целевую архитектуру. Контракты исполнения, поставка Runtime, поддерживаемые модели и MCP-адаптеры подлежат спецификации; готовые команды запуска не заявлены.
