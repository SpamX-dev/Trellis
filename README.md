# Trellis

Система управления семантически связанными инженерными знаниями и изменениями методов работы. Trellis связывает требования и архитектурные решения со способами их реализации, навыками, проверками и изменениями конкретных проектов.

## Назначение знаний

База знаний содержит единый семантический граф с общей идентичностью, ревизиями и происхождением данных. Документы являются источниками или типизированными представлениями частей этого графа.

Внутри модели различаются три назначения знаний:

- Исследования, наблюдения и обоснования предоставляют контекст для рассуждений.
- Принятые требования и ограничения задают обязательства в определённой области применимости.
- Навыки, процедуры и проверки определяют способы выполнения работы и оценки результата.

Назначение определяется для отдельных утверждений и сущностей. Один документ может содержать требование, его обоснование и пример реализации. Наличие инструкции в исходном документе само по себе не делает её принятой нормой: интерпретация и принятие проходят через ChangeSet и review.

## Требование и его реализация

Требование описывает необходимое свойство системы. Control выражает обеспечиваемое свойство; Realization Pattern описывает общий способ его обеспечения; Project Realization фиксирует выбранный способ и точку приложения в конкретном проекте.

Например, требование относится к endpoint, а обеспечивается конфигурацией безопасности приложения. Масштаб требования, место реализации и инженерная область, ответственная за изменение, описываются отдельно.

```text
Requirement -> Control -> Realization Pattern -> Project Realization
                              |                       |
                              v                       v
                       Skills / Checks       Implementation / Evidence
```

Один способ реализации может поддерживать несколько требований. Для одного требования могут потребоваться несколько способов реализации и несколько методов работы. Связи описывают принятый замысел; выполнение требования подтверждается отдельной оценкой с Evidence.

## Работа с изменениями

Оператор выражает намерение; агент с подходящим навыком формирует Semantic ChangeSet относительно базовой ревизии. Knowledge хранит предложение, строит draft state, semantic diff и представления документов. Человек проверяет предложение; принятую ревизию создаёт Knowledge после проверки условий применения.

Для изменения требования этот цикл продолжается управлением затронутыми методами и проектами:

```text
Proposed requirement change
  -> semantic delta + candidate impact paths
  -> ImpactPlan: affected methods, projects, unknowns
  -> human review of requirement and plan
  -> accepted revision + WorkItems for responsible areas
  -> changes to methods and project implementations
  -> result review + verification
  -> new artifact versions + explicit adoption
  -> reassessment of requirement coverage
```

Skill является и входом Engineering Work, и управляемым результатом работы по изменению методов. Требование, контекст проекта, выбранные способы реализации и инженерные решения определяют содержание изменения навыка. Процесс допускает результат «проверено, изменение не требуется» с обоснованием.

Граф показывает возможные пути влияния. Агент интерпретирует их и отмечает неполноту данных; человек проверяет предложенный план. Одобрение плана разрешает работы, а готовые изменения проходят собственное review. Воспроизводимость обеспечивается фиксацией входов, версий и решений, а не предположением о детерминированной генерации навыка из текста требования.

## Актуальность и покрытие

Для методов сохраняются связи с ревизиями требований, способами реализации, условиями применимости и проверками. Изменение зависимости требует пересмотра актуальности; это ещё не доказывает ошибочность метода.

Оценки разделены по двум измерениям:

- **Покрытие методами:** требования учтены в применимых навыках и проверках для заданной области работ.
- **Выполнение в проекте:** конкретная версия реализации проверена относительно конкретной ревизии требования.

Обновление навыка не исправляет уже существующие приложения. Для них формируются отдельные WorkItems. Публикация версии пакета не означает её подключения: запуск использует зафиксированные версии, а новая конфигурация применяется к последующим запускам.

## Компоненты и структура

[Общая граница Trellis](module.md) определяет разделение ответственности компонентов.

| Блок | Ответственность |

| [Framework](trellis-framework/module.md) | Общая модель, контракты работы, ревизий, review и покрытия. |
| [Semantic Model](trellis-framework/semantic-model/module.md) | Декларативные типы, отношения и ограничения внутри Framework. |

| [Knowledge](trellis-knowledge/module.md) | Каноническое состояние графа, история, планы, оценки и Evidence. |

Метамодель размещается в `trellis-framework/semantic-model/`; экземпляры знаний — в `trellis-framework/examples/`. Общие типы не переопределяются внутри примеров. Семантика опирается на ArchiMate и расширяется понятиями, необходимыми Trellis.

## Ограничения

Trellis не анализирует исходный код и не строит AST/LSP-дерево. Внешние инструменты выполняют проверки реализации; Trellis хранит их результаты, область проверки и происхождение как Evidence. Наличие связи в графе или успешная проверка формата пакета не доказывает выполнение требования.
