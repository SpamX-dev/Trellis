# Инструкции для агентов

## Назначение

Этот файл содержит устойчивые правила работы с проектом.

## Что за проект

Проект который должен предоставить некоторый граф для рассуждений и навигации по проекту для LLM.

## Правила компоновки дирректорий и файлов

1. Структура репозитория задаёт разработчику карту системы и тем самым подталкивает код принимать определённую архитектурную форму.
2. Если хочешь определённую архитектуру кода, организуй repository topology так, чтобы самое естественное место для нового кода соответствовало этой архитектуре.
3. Directory structure — это один из инструментов, которыми архитектура навязывается разработчику.
4. module.md нужно размещать в директориях которые ограничивают крпные блоки архитектуры, для описания границы.
5. Если блок планируется, но пока его нет, то стоит создать его структуру и разместить module.md
6. module.md не должен содержать статус реализации

**Нужно внимательно следить за структурой репозитория**. Она должьна быть одновременно самодокументацией и ограничением. Выход за границы должен всегда быть согласован.

## Принятие решения о развитии

1. Построй целевое решение. Сверь со структурой проекта.
2. Ты всегда найдешь документацию непосредственно в самом коде. Если ее недостаточно - нужно сначала рассказать об этом и запросить изменения документации кода.

## Целевое решение

1. Целевое решение это известное направление развития, которое отвечает запрошенным требованиям.
2. Если такое решение нельзя построить, то принимаются ADR, которые фиксируются в дереве проекта в ближайшей к границе влияния директории: adr-[name].md

## Комментирование кода

1. В коде дожны быть подробные комментарии для всех верхних структур кода (классы, интерфейсы, перечисления и т.д.).
2. Комментарии пишем на русском языке.
3. Если комментариев нет - их надо добавить, даже при ревью.
4. Что в комментариях - границы: отвественность, функциональность, поведение, зависимость, принятые ограничения или исключения.

## Использование skills

Если skill конфликтует с ADR - применяй ADR
